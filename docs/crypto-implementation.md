# Состояние реализации E2EE

Ветка `security-mls`, обновлено 26 октября 2026. **Общее ядро, локальные адаптеры и первый путь настройки устройства/Recovery Key. Производственная переписка пока использует прежнюю облачную схему.** Этот этап не включает отправку E2EE через действующий API и не меняет историю в БД.

## Уже в коде

- `crates/coherent-crypto`: OpenMLS **0.9.2**, обязательный набор RFC 9420 `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`. Никаких draft-протоколов. AES-256-GCM для отдельного содержимого и архивных объектов; 128-битный MLS-набор не называется AES-256.
- Каждый экземпляр устройства имеет собственную Ed25519-пару и KeyPackages. Отдельные проверки закреплённого отпечатка устройства и списка устройств, разрешённых в конкретной беседе. Каталог сервера сам по себе не считается доказательством доверия.
- Создание группы, Add/Remove Commit, Welcome со встроенным деревом, применение Commit после подтверждения точных отправленных байтов, отправка/приём приложений, откат локального состояния при ошибке.
- Случайный ключ содержимого сообщения доставляется через MLS. Тело шифруется один раз; контекст связывает беседу, сообщение и отправителя. Архив ключей аккаунта хранит зашифрованные ключи содержимого и хеши тел, отдельно от живого состояния MLS.
- Один материал восстановления архива аккаунта: 12 английских слов BIP-39 из 128 случайных бит (старые 24 слова поддерживаются), HKDF-SHA256 с разделением назначения, аутентифицированная резервная копия. Активные приватные ключи и ratchet-состояния не попадают в эту копию.
- Браузерный адаптер: Rust/WASM в Worker, неизвлекаемый AES-256 ключ Web Crypto в IndexedDB, аутентифицированное локальное состояние, эксклюзивный Web Lock на аккаунт и проверка версии перед записью. Состояние и очередь отправки сохраняются одной транзакцией до возврата пакета вызывающему коду. Для входящего сообщения запись архива также попадает в очередь; открытый текст туда не записывается.
- Нативный адаптер: Rust, зашифрованный локальный файл, блокировка между процессами, атомарная замена файла и синхронизация записи. Ключ хранилища — Windows Credential Manager, macOS Keychain или Linux Secret Service. При недоступности хранилища ОС перехода к открытому файлу нет.
- Общий контракт команд и Tauri-мост. Нативный мост по умолчанию закрыт; feature `mls-preview` включает только локальный адаптер для разработки.

Экспорт `snapshot_local` содержит секреты и служит **исключительно** для локального аутентифицированного хранилища. Его нельзя отправлять серверу, переносить на другое устройство или использовать как Recovery backup. Повторная отправка использует точные байты из сохранённой очереди, а не новый вызов `send`. Восстановление старого снимка профиля/клонирование профиля с живым MLS-состоянием не поддерживается: требуется регистрация нового устройства и повторное вступление в группы.

## Платформы

| Платформа | Общий протокол | Локальный адаптер | Приложение/интеграция |
| --- | --- | --- | --- |
| Браузер | Rust → WASM | Web Crypto + IndexedDB + Web Locks | Worker и мост готовы, подключение чатов впереди |
| Windows | Rust напрямую | Credential Manager + зашифрованный файл | Tauri-мост за feature, сборка Windows здесь не выполнялась |
| Linux | Тот же Rust | Secret Service + зашифрованный файл | Основа готова, отдельного релиза нет |
| macOS | Тот же Rust | Keychain + зашифрованный файл | Адаптер выбран, на macOS не проверялся |
| Android | Тот же Rust | Интерфейс `VaultKeyStore`; далее Android Keystore | Нужны платформенная обвязка, UI и сборки |
| iOS | Тот же Rust | Интерфейс `VaultKeyStore`; далее iOS Keychain | Нужны платформенная обвязка, UI и сборки |

Общее ядро использует `std` и не зависит от Tauri, UI, API клиента, файлов сервера или его мастер-ключа. Мобильные адаптеры не должны хранить ключ в обычных preferences. Выбранная оболочка и доступность MLS на каждой целевой ОС проверяются отдельно; наличие общего Rust-кода не означает готовность приложения.

## Сборка

Используется Rust 1.99.1. Зависимости закреплены lockfile; для OpenMLS и wasm-bindgen заданы точные версии. Обновлять библиотеку и CLI wasm-bindgen нужно вместе.

```sh
rustup target add wasm32-unknown-unknown
cargo install wasm-bindgen-cli --version 0.2.129 --locked
cd frontend
npm run crypto:build
npm run crypto:bundle
npm run build
```

`crypto:build` формирует локальные артефакты в `frontend/public/crypto/v1/`; они не хранятся в Git. Обычная сборка сайта пока их не требует, поскольку новая переписка не подключена. Dockerfile теперь собирает и публикует ядро для настройки устройства и ключа. CSP разрешает WebAssembly и собственный Worker. Полная интеграция MLS-чата остаётся отдельным этапом.

Выполнены компиляция общего ядра, компиляция WASM и сборка JS/WASM-пакета, компиляция Linux-адаптера хранилища и TypeScript. Это **не** подтверждение совместимости устройств, восстановления или полноценной E2EE-переписки. Windows-приложение и мобильные приложения не собирались; новые функциональные тесты пока не добавлялись. Workflow `crypto-core.yml` отдельно проверяет компиляцию ядра и WASM.

## Что требуется до включения

1. **Подтверждение устройств.** Подписанный журнал доверия с порядком изменений, проверка QR/подтверждения вне доверия к серверному каталогу, защита от отката, отзыв устройства и показ смены идентичности. Команды `pin_device`/`authorize_conversation` — вход для результата этой проверки, а не её замена. Нельзя автоматически подставлять туда ответ API устройств.
2. **Доставка MLS.** Аутентифицированные запросы устройства, одноразовые KeyPackages, атомарное согласование Commit/Welcome, CAS последовательности и эпохи, повторные запросы без двойной публикации. Входящие события, архив и курсор должны фиксироваться до подтверждения доставки. Переподключение после потери состояния требует fresh join.
3. **Архив и Recovery.** Серверное хранение непрозрачных записей с квотами/пагинацией/контролем конфликтов, перенос доступа к архиву подтверждённому новому устройству. Текущие примитивы восстанавливают только ключ архива, не полномочия нового устройства в MLS.
4. **Ротация архива при отзыве устройства.** Отозванное устройство уже знало старый ключ архива. Для защиты будущей истории от него нужны новые поколения ключей архива, их доставка оставшимся устройствам и безопасное обновление Recovery backup. Одного запрета HTTP-доступа к архиву для этого недостаточно. Нельзя включать полный продукт до завершения этой части.
5. **Файлы и интерфейс.** Шифрование файлов до загрузки, зашифрованные имена/MIME, лимит 15 ГиБ и три дня, фото после локальной расшифровки, общие push без текста, локальный поиск и явное состояние «устройство ещё не подтверждено».
6. **Перенос истории.** Явное различение `legacy_cloud` и MLS; проверенный клиентский перенос, согласование участников, защита от plaintext downgrade и только затем удаление прежних облачных копий по принятому сроку. Каналы серверов остаются облачными. Мастер-ключ и существующие резервные копии не удаляются этим этапом.
7. **Email reset.** Разделение адресов и очередь кодов регистрации добавлены в 0016. Нужны восстановление пароля и общая очередь для привязки почты/служебных уведомлений. Сброс пароля восстанавливает аккаунт, но не ключи переписки.
8. **Проверка интеграции.** Несколько устройств/вкладок, одновременные Commit, повреждённые пакеты, пропуски и повторы, отзыв устройства, потеря всех устройств, перенос архива, сбои записи и сети, несовпадающие версии клиентов. Отдельно — оценка интеграции криптографии до production, проверка обновлённых advisories и подписанный Windows-релиз.

## Второй этап: регистрация и локальный Recovery Key

- Создание аккаунта теперь требует почту, UUID одноразового запроса и шестизначный код. До подтверждения пользователь и сессия не создаются. Пароль не хранится в заявке.
- SMTP-коды регистрации поступают в ограниченную очередь: HMAC проверки, AES-GCM для ожидающего отправки кода с отдельным назначением ключа, lease обработчика, повторы до истечения 10 минут. SMTP вызывается после завершения транзакции. Лимиты: 5 запросов на адрес/час и пауза 60 с, 20 на IP/час, 400 общих/час; записи удаляются через сутки.
- Миграция 0016 переносит старые неподтверждённые адреса в `pending_email`. Они видны владельцу как подсказка, но не занимают уникальное подтверждённое владение и не дают вход через email. Доступ по существующему логину сохраняется.
- В профиле и после регистрации есть настройка ключа, показ слов, копирование, скачивание файла, подтверждение двух слов из своей копии. На сервер уходят публичная Ed25519-идентичность устройства, отдельный публичный ключ проверки восстановления и зашифрованная копия ключа архива. Публичный ключ восстановления детерминированно выводится на клиенте из слов через отдельный HKDF-контекст; приватная часть не передаётся серверу.
- Первое устройство регистрируется после подтверждения почты, текущего пароля и одноразовой подписи запроса, связывающей аккаунт, устройство, ключ, nonce и резервную копию. Повторный вход не добавляет устройство автоматически. Следующие устройства и перенос ключей ещё требуют отдельного этапа QR-протокола.
- Повторный просмотр выполняется в Worker/нативном мосте после проверки текущего пароля и подписи активного доверенного устройства. Обход через обычные `execute(create_recovery/show_recovery)` закрыт в платформенных мостах. Старые локальные копии без сохранённой фразы не превращаются в новую фразу неявно.
- Письмо сообщает только о подтверждённом сохранении ключа, самих слов в письме нет. Это уведомление отправляется с best-effort обработкой; надёжная общая очередь уведомлений остаётся отдельной задачей.
- `E2EE_SETUP_ENABLED` управляет только этим начальным путём и по умолчанию включён. Режим сообщений остаётся `legacy_cloud`; схема хранения чатов не переключается и история не удаляется. Windows-адаптер пока за `mls-preview`, подписанный выпуск не собирался здесь.
- Docker собирает WASM тем же закреплённым toolchain и CLI; web CSP разрешает WASM и собственный Worker, ограничивает источники исполняемого кода.

Проведены существующие 25 backend-проверок с обновлёнными регистрационными помощниками, компиляция Rust/TypeScript и ручная проверка цепочки WASM → API в изолированной БД: 12 слов, сохранение после восстановления локального снимка, подписи, запрет изменённой копии, пароль, одноразовость и запрет нового неподтверждённого устройства. Внешние проверочные письма не отправлялись. Это ещё не проверка полноценной MLS-переписки и не миграция действующих чатов.

Повторная подготовка восстановления возвращает ту же сохранённую зашифрованную копию. Подпись начальной настройки допускается только для собственной локальной копии и включает публичный ключ восстановления, чтобы интерфейс не мог незаметно подставить другой backup.
