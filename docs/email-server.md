# Почтовый сервис Когерента

Ветка `email-server` создана от `main` на коммите `0807167087cecb0976dc53236362968728dced28`. Она содержит весь проект с текущим почтовым модулем, его интерфейсом, миграциями и настройкой VPS. Этот документ — точка входа для дальнейшей работы над почтой.

## Что уже реализовано

- Исходящая почта от `noreply@coherent-web.ru` на одном VPS: Postfix и OpenDKIM.
- Приём SMTP только с localhost и из доверенной сети контейнеров, с отдельным правилом UFW для внутреннего соединения. Исходящая доставка требует TLS.
- Подпись DKIM и опубликованные DNS-записи A, PTR, SPF, DKIM и DMARC.
- Запрос кода в профиле после ввода текущего пароля и подтверждение адреса шестизначным кодом.
- Хранение HMAC кода, срок 10 минут, пять попыток проверки, пауза между отправками и ограничения за час. Код одноразовый и связан с версией сессии.
- Отображение состояния подтверждения почты и доступности отправки в профиле.

Это сервис исходящих служебных писем. Входящие почтовые ящики, IMAP и веб-почта в текущую реализацию не входят.

## Зафиксированное состояние после развёртывания 25 октября 2026

- Почтовая отправка включена в рабочем приложении.
- Проверена подпись сообщений с localhost, из контейнера API и через сам модуль отправки кодов. Диагностические сообщения задерживались в локальной очереди HOLD и удалялись после проверки, без внешней доставки.
- Gmail принял отдельное проверочное письмо владельцу, но поместил его в спам. Заголовки полученного письма недоступны, поэтому результаты SPF/DKIM/DMARC именно со стороны Gmail неизвестны. Доставка во входящие пока не подтверждена.

## Что осталось сделать

### 1. Доставка во входящие

- Получить заголовки контрольного письма у доступного получателя и проверить аутентификацию на его стороне.
- Проверить фактическую доставку на Gmail и другие нужные почтовые сервисы. Новые внешние проверочные письма отправлять только на согласованные адреса.
- По результатам разбирать причину фильтрации. Успешная локальная проверка DKIM не устанавливает причину попадания письма в спам.

Критерий готовности: зафиксированы результаты приёма и аутентификации у получателей; доступные ограничения доставки явно описаны.

### 2. Надёжная очередь отправки

Сейчас SMTP вызывается до завершения транзакции БД, а запрос держит блокировку пользователя во время отправки. Нужны запись задания в одной транзакции с запросом кода, отдельный обработчик, ограниченные повторы и защита от повторной обработки задания. Следует явно обрабатывать случай, когда SMTP уже принял письмо, а сохранение состояния или получение ответа завершилось ошибкой. Обещать строго однократную доставку поверх SMTP нельзя.

Критерий готовности: сбой SMTP не задерживает транзакции пользователя; задания имеют понятное состояние и ограниченный срок жизни; устаревшие коды не рассылаются повторно.

### 3. Усиление защиты от массовых отправок

- Добавить отдельную историю попыток отправки и точный общий лимит на адрес. Сейчас счётчик адреса рассчитывается по текущим строкам подтверждения, а строка пользователя перезаписывается при смене адреса.
- Добавить ограничения по IP и общий предел нагрузки на отправителя с учётом нескольких аккаунтов и процессов API.
- Определить срок хранения технической истории без сохранения открытых кодов или тела писем в журналах.

### 4. Правила владения адресом

Старый API регистрации всё ещё принимает необязательный адрес без подтверждения. Такой адрес занимает уникальное поле пользователя, а подтверждение для другого аккаунта отклоняется даже при наличии правильного кода. Нужно отделить неподтверждённую заявку от подтверждённого владения адресом и описать безопасный перенос старых данных. Сам факт наличия адреса в старой записи не должен считаться подтверждением владения.

### 5. Мониторинг и обслуживание

- Добавить в админ-панель состояние SMTP/OpenDKIM, длину и возраст очереди, ошибки и показатели доставки. Различать «SMTP принял» и «получатель принял»; папка входящих при этом остаётся отдельным результатом.
- Подготовить защищённое резервирование и проверку восстановления DKIM-ключа, процедуру смены селектора и ключа. Проверка резервной копии и ротации DKIM в предыдущем этапе не проводилась.
- Проверить обслуживание после перезагрузки VPS и пересоздания сети Docker: адреса доверенных сетей, мост, UFW и порядок запуска служб. Установочный скрипт уже поддерживает повторный запуск, но автоматическое сопровождение изменений сети пока не реализовано.

### 6. Автоматические проверки почтового контура

Существующие тесты подменяют SMTP-отправку. Дополнительно нужны проверки настоящей связки Postfix/OpenDKIM, отказа SMTP, параллельных подтверждений, конфликтов адресов и ограничений при смене адреса. Подключить CI для ветки `email-server`: обновлённый workflow запускается по push во все ветки, а также по pull request в `main`. Автоматическое production-развёртывание отслеживает только `main`.

## Связанные следующие этапы проекта

Актуальная [модель безопасности](security-model.md) использует облачное шифрование переписок и одноразовые E2EE-ключи звонков. Recovery и подтверждение криптоустройства для новой истории не требуются. Почтовое подтверждение регистрации и адреса реализовано; восстановление забытого пароля по почте остаётся отдельной задачей. Старый протокол архивов сохранён как неактивный модуль и описан в историческом [security-mls.md](security-mls.md).

## Обновление 26 октября: обязательная почта при регистрации

В `security-mls` добавлен отдельный регистрационный поток: очередь кодов без удержания транзакции во время SMTP, лимиты по адресу/IP/сервису, одноразовая проверка до создания пользователя, статус отправки и перенос неподтверждённых адресов в `pending_email`. Обычная привязка почты в старом профиле пока использует прежний обработчик; её очередь и общий мониторинг ещё требуют доработки.

В прежнем протоколе Recovery Key не передавался почтовому модулю: письмо о сохранении содержало только уведомление. В облачном режиме Recovery не используется.
