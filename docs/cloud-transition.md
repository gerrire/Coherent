# Переход на облачные чаты и одноразовый E2EE звонков

## Решение владельца

28 октября 2026 владелец разрешил удалить существующие сообщения и вложения, сохранив аккаунты. Сохраняются также друзья, беседы, названия групп, участники, сообщества, каналы, профили и сессии. Перенос MLS-истории в облако и legacy reader в этом выпуске не требуются. Старые криптографические таблицы и исходники остаются изолированными, чтобы сохранить возможность будущего E2EE текста.

Звонки сохраняют MLS exporter и E2EE LiveKit. Ключи устройств для звонка одноразовые, находятся в памяти клиента и не требуют Recovery или подтверждения другого устройства. Начальные публичные описания приходят из авторизованного каталога; независимая сверка эмодзи остаётся проверкой первоначальной подмены. Подробности в [модели безопасности](security-model.md).

## Безопасная последовательность

1. Проверить успешные backend/frontend/Rust проверки и Windows-сборку на точном коммите, скачать и проверить подпись Windows 0.1.4. Сохранить SHA текущего приложения и совместимого выпуска.
2. Создать свежие защищённые копии PostgreSQL, действующих вложений и конфигураций. Отдельно сохранить существующий master key, не генерировать новый. Восстановить копию в изолированный PostgreSQL, проверить аутентичную расшифровку облачных записей, число аккаунтов, затем миграцию до 0027 и `alembic check`. Проверка не печатает содержимое сообщений и ключи.
3. Установить совместимый API и веб-клиент, применить 0027. Миграция сама ничего не удаляет: при наличии MLS-сообщений создаётся политика `legacy_mls`. До явного переключения сохраняется прежняя модель. На чистой БД начальная политика — `cloud_v1`.
4. Обновить Windows. Перед переключением проверить отсутствие подключённых звонков, остановить API-запись и фоновые операции, обновить согласованный снимок. При ошибке подготовительной проверки запустить API обратно.
5. Выполнить отдельную команду сброса. Она под блокировкой политики удаляет сообщения, вложения, отметки прочтения и служебный MLS-транспорт обычных чатов. Пользовательские записи и служебные MLS-группы звонков не удаляются. Зафиксировать `cloud_v1`, новый `history_revision`, время сброса.
6. Удалить файлы из приватного манифеста после фиксации БД; запустить API. Проверить число и целостность сохранённых аккаунтов/связей, нулевую старую историю, права участников, HTTPS/readiness и новый вызов между двумя клиентами.

Пример серверной команды после проверенной копии и установки точного образа:

```sh
cd /opt/coherent
reset_id=$(python3 -c 'import uuid;print(uuid.uuid4())')
reset_dir="/var/lib/coherent-cloud-reset/$reset_id"
install -d -m 0700 -o 10001 -g 10001 "$reset_dir"
# deploy_sha — уже проверенный и установленный совместимый коммит.
COHERENT_IMAGE_TAG="$deploy_sha" docker compose --env-file deploy/.env -f deploy/compose.prod.yaml stop api
COHERENT_IMAGE_TAG="$deploy_sha" docker compose --env-file deploy/.env -f deploy/compose.prod.yaml run --rm --no-deps -v "$reset_dir:/run/cloud-reset" api python -m coherent_api.tools.reset_chat_history --operation-id "$reset_id" --manifest /run/cloud-reset/manifest.json --apply
COHERENT_IMAGE_TAG="$deploy_sha" docker compose --env-file deploy/.env -f deploy/compose.prod.yaml up -d --no-build --no-deps api
```

Перед `--apply` можно вызвать инструмент с тем же ID без этого флага: он покажет только агрегаты. Для продолжения после сбоя нужны **тот же ID и тот же манифест**. Повтор успешно завершённой операции только продолжает очистку старых файлов и не удаляет новые сообщения. Другой ID после выполненного сброса отклоняется. После любой ошибки API необходимо запустить обратно; рабочий операторский сценарий использует `finally` для этого действия.

## Проверки и границы

- Cloud write проверяет актуальную политику под общей блокировкой; изменение политики использует исключительную. Старый MLS API после переключения не может продолжить обычную переписку или отправить ранее подготовленный пакет.
- Регистрация временного ключа звонка привязана к пользователю, звонку, активной сессии и одноразовой подписи. Запросы другого пользователя/звонка/сессии и повтор доказательства отвергаются.
- Изменение состава приводит к MLS commit и новому ключу медиа. Ранее покинувший участник не получает новый ключ. API дополнительно отключает его в LiveKit.
- Файловая квота и трёхдневный срок сохраняются. Временные резервные копии медиа после завершения работ удаляются; периодические копии медиа по-прежнему не создаются. Копии БД могут содержать старую историю в пределах прежней политики хранения.
- Сервер не может отозвать уже сохранённые участниками копии или очистить чужой браузер удалённо. После переключения нужно обновить страницу и Windows-клиент.
- Смена пароля по текущему паролю и email-подтверждение сохраняются. Восстановление забытого пароля по почте не добавлено этим переходом.

## Откат приложения без потери новых данных

После сброса допустим только код, который понимает `chat_policy` и `cloud_v1` (совместимая база этого выпуска — 0.1.4). Нельзя возвращать API 0.1.3, включать MLS-запись обычных чатов или откатывать схему ниже 0027. Прежний master key сохраняется.

Для будущего отката на проверенный совместимый SHA:

```sh
cd /opt/coherent
git switch --detach "$compatible_sha"
COHERENT_IMAGE_TAG="$compatible_sha" docker compose --env-file deploy/.env -f deploy/compose.prod.yaml up -d --no-build
```

Использовать сохранённые проверенные образы; если их нет, сначала получить соответствующий immutable deployment artifact и проверить манифест/хеши штатным механизмом развёртывания. Затем проверить readiness, чтение новой облачной истории и E2EE звонок. Значение `chat_policy` и рабочая БД сохраняются. Восстанавливать старый дамп поверх БД с новыми сообщениями нельзя: это потеряет новые данные. Полное восстановление — отдельная аварийная процедура, а не автоматический откат приложения.
