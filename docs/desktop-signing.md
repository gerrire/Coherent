# Подпись обновлений Windows

Исходный ключ обновлений найден на Windows-ПК владельца. 27 октября 2026 года он и его пароль добавлены в **[GitHub Actions → Secrets and variables → Actions](https://github.com/gerrire/Coherent/settings/secrets/actions)** репозитория `gerrire/Coherent`:

- `TAURI_SIGNING_PRIVATE_KEY` — содержимое существующего приватного ключа, а не путь к файлу на ПК.
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` — пароль этого ключа.

GitHub хранит секреты зашифрованными. В настройках видны имена и даты, прочитать сохранённые значения обратно нельзя. Приватного ключа и пароля в Git, установщиках и артефактах сборки нет. Публичный ключ в `frontend/src-tauri/tauri.conf.json` остаётся прежним, поэтому подписи принимаются клиентами 0.1.0 и 0.1.1.

## Где посмотреть оригинал на Windows

| Файл | Назначение |
| --- | --- |
| `%USERPROFILE%\.tauri\coherent.key` | Приватный ключ подписи, защищён паролем |
| `%USERPROFILE%\.tauri\coherent.key.pub` | Публичный ключ для проверки подписи |
| `%USERPROFILE%\.tauri\coherent.key.password.dpapi` | Пароль, зашифрованный Windows DPAPI для текущей учётной записи |

На ПК владельца это каталог `C:\Users\Алексей\.tauri`. Открыть приватный ключ можно обычным текстовым редактором. Для просмотра пароля **локально под той же учётной записью Windows**:

```powershell
$saved = Get-Content -LiteralPath "$env:USERPROFILE\.tauri\coherent.key.password.dpapi" -Raw
$secure = $saved.Trim() | ConvertTo-SecureString
[System.Net.NetworkCredential]::new('', $secure).Password
```

Для переноса или резервной копии нужны и приватный ключ, и его пароль. DPAPI-файл сам по себе не расшифруется на Linux или под другой учётной записью Windows. Храните резервную копию в защищённом хранилище; не добавляйте эти файлы в репозиторий, Release или сообщения чатов.

## Сборка из Linux через GitHub Actions

Linux-среде не нужен путь `C:\Users\Алексей\.tauri`: ключ передаётся Windows runner из GitHub Secrets только на шаге подписи. Windows-приложение собирается и проверяется на `windows-latest`.

Сначала изменения обкатываются в веб-версии. Сборка и выпуск Windows выполняются по отдельному запросу владельца; обычные push в ветки их не запускают. Доступны ручной запуск workflow и явный тег выпуска.

1. Зафиксируйте исходники с согласованной версией в Tauri, Cargo и npm и заметками `docs/releases/desktop-<version>.md`.
2. Для черновика запустите workflow **Windows client** из `main` или `windows-client`, включив `prepare_release`. Для публикации подписанного выпуска создайте и отправьте тег `desktop-v<version>` на проверенном коммите, включённом в `main`: сборка по тегу проверяет версию и подпись, затем публикует выпуск в канал обновлений.

```bash
gh workflow run windows-client.yml --repo gerrire/Coherent --ref windows-client -f prepare_release=true
```

3. Workflow проверит наличие ключа до компиляции, соберёт приложение, упакует и подпишет NSIS-пакет, проверит подпись и привязку версии и создаст **черновик** `desktop-v<version>` с установщиком, `.sig`, `latest.json` и контрольными суммами. Повторная публикация существующего выпуска запрещена командой создания; она не заменяет уже опубликованные пакеты.
4. После необходимых проверок опубликуйте черновик как обычный выпуск с `--latest`. Серверные выпуски `deployment-*` должны сохранять `--latest=false`, иначе они перекроют канал обновлений старых клиентов.

Быстрая проверка секретов без сборки приложения — workflow **Desktop signing check**. Он работает на Linux runner: подписывает временный текстовый файл, сверяет публичный ключ и подписанную версию и проверяет отказ после изменения файла. Ключи и временные файлы не загружаются в artifacts.

Исходники и сценарий подписи входят в `main`; единственная Windows-ветка — `windows-client`. Временная ветка `windows-release` и сценарии неподписанной ручной публикации удалены после восстановления исходного ключа.

## Локальная сборка Windows

Приоритет доставки: выпуск Windows завершён только после появления версии во встроенном обновлении. Локального установщика или черновика GitHub Release недостаточно. После публикации обязательно запускайте `scripts/verify-desktop-release.ps1`: он читает публичный адрес из конфигурации приложения, проверяет версию и подпись манифеста, скачивает пакет, сравнивает SHA-256 с локальным и проверяет криптографическую подпись и подписанную версию. Проверка добавлена в workflow после публикации. Реальную установку и перезапуск клиента отмечайте отдельно.

При использовании общего каталога сборки передайте `-BundleDirectory` в `prepare-desktop-release.ps1` и `verify-desktop-release.ps1`.

`scripts/build-desktop.ps1` сначала использует `TAURI_SIGNING_PRIVATE_KEY` и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` из окружения, если они заданы. Иначе он загружает локальный ключ и расшифровывает DPAPI-пароль. После сборки восстанавливает исходные переменные окружения и очищает временную расшифрованную память.

Для подписи уже готового доверенного установщика без повторной компиляции Tauri CLI поддерживает `signer sign --app-version <version>`. Это обязательно при `requireSignedVersion: true`: подпись должна подтверждать и файл, и версию. Сначала проверьте происхождение и контрольную сумму файла; не подписывайте произвольные скачанные исполняемые файлы.

Сам установщик в ходе этой работы не запускался; проверка новых MLS-сценариев и устройств на физическом Windows-ПК остаётся отдельной проверкой.
