# Модель защиты чатов

## Обычные облачные чаты — один VPS

Логины, отображаемые имена, состав бесед, даты и имена файлов остаются метаданными в PostgreSQL. Текст новых сообщений и подписи к вложениям шифруются AES-256-GCM до записи в БД. Ключ для каждой беседы выводится HKDF-SHA256 из случайного мастер-ключа; идентификаторы беседы и сообщения включены в аутентифицируемые данные. Каждое сообщение получает новый случайный nonce.

Мастер-ключ — ровно 32 случайных байта в `/etc/coherent/keys/chat-master.key`, вне БД, Git и `.env`. Права каталога `0700`, файла `0600`; API получает только чтение через отдельное монтирование. При отсутствии или замене ключа уже зашифрованная история не позволяет API запуститься. Автоматической генерации замены нет.

Новые файлы также шифруются AES-256-GCM с отдельным производным ключом для каждого вложения. Доступ к скачиванию проверяется по текущему составу беседы или сервера. Перед ответом проверяется целостность всего файла; временная расшифрованная копия имеет приватные права, в production создаётся в `/tmp` на tmpfs и удаляется после ответа. Незавершённые копии убирает фоновая очистка. Общая квота учитывает служебные байты шифрования.

Срок хранения вложений остаётся три дня. После удаления файла сообщение и подпись сохраняются, а вместо вложения показывается «Вложение удалено». Файлы до включения шифрования остаются в старом формате до истечения своего срока. Счётчик таких файлов доступен администратору.

Сервер расшифровывает облачную историю для авторизованных участников и уведомлений. Эта схема защищает содержимое при отдельной утечке БД или файлового хранилища. Она **не защищает от полного доступа к VPS, к работающему API или к устройству участника и не является E2EE**. В уведомлениях может быть текст сообщения.

## Включение и перенос истории

1. Сохранить резервную копию БД и отдельно защищённую копию мастер-ключа. Копия ключа только на том же VPS не защищает от потери VPS; для восстановления после такой потери нужна отдельная защищённая копия владельца.
2. Один раз выполнить `python3 deploy/init-chat-key.py`. Существующий ключ не перезаписывается.
3. В серверном `deploy/.env` задать `CHAT_MASTER_KEY_PATH=/run/coherent-keys/chat-master.key` и `CLOUD_ENCRYPTION_REQUIRED=true`.
4. Собрать API, применить миграции и запустить обновление. Новые записи сразу зашифрованы; старые читаются в прежнем формате.
5. Проверить счётчик старых сообщений командой `python -m coherent_api.tools.encrypt_history` внутри API-контейнера. После проверки резервных копий выполнить с `--apply`.

Перенос идёт транзакциями по 100 сообщений. Каждый зашифрованный текст расшифровывается и сравнивается с исходным до удаления открытого текста. Команда возобновляемая и повторно не шифрует уже перенесённые записи. Старые резервные копии автоматически не меняются; до истечения их срока они могут содержать открытые сообщения. Миграция назад блокируется при наличии зашифрованной истории: для отката приложения нельзя терять столбцы или мастер-ключ.

Ротация мастер-ключа не реализована: простая замена файла сломает чтение истории. Нужен отдельный процесс перешифрования с версиями ключей.

## Приватные E2EE-чаты — следующий этап

По принятому решению они будут доступны только в приложениях, с ключами на устройствах. Почтовый код может разрешать перенос на своё другое устройство, но сам по себе не должен позволять серверу вычислять или расшифровывать ключ переписки. В веб-версии такой режим не предлагается.

В текущем обновлении приватные E2EE-чаты, обмен ключами между устройствами и восстановление ключей **не реализованы**. Следующий этап требует выбора проверенного протокола и библиотеки, модели устройств, проверки собеседника, защиты от повторов и смены состава группы. Самодельный протокол для этих задач не используется. Существующее шифрование медиа звонков LiveKit — отдельная система; ключ звонка выдаёт API, это не модель приватной переписки без доверия к серверу.

## Почтовые коды

Привязка адреса требует текущий пароль и код из письма. Код действует 10 минут, имеет пять попыток, интервал повторной отправки 60 секунд и лимит отправок за час. В БД хранится HMAC, а не сам код; запрос привязан к версии сессии и становится недействительным после смены пароля. Почта не становится обязательной для входа.

SMTP принимает отправку только с localhost и доверенной сети контейнеров. Письмо подписывает OpenDKIM, исходящее соединение Postfix требует TLS. Наличие SPF/DKIM/DMARC не гарантирует попадание во входящие: правила фильтрации получателя остаются внешним ограничением.
