# Проверка Coherent Desktop

## Исправления 0.1.5: память и микрофон

28 октября устранено накопление слушателей `coherent:event*` при переподключениях. Старые слушатели раньше оставались активны до размонтирования ChatShell; очередное событие закрытия запускало повторные попытки через все старые обработчики. Теперь слушатели очищаются сразу при закрытии, события имеют идентификатор подключения, а устаревшая команда остановки не отключает новое подключение. Исправление не требует Redis.

Нативная очередь PCM, очередь IPC и AudioWorklet ограничены общими подтверждениями потребления: до восьми неподтверждённых пакетов. Переполнение отбрасывает новые пакеты до возврата кредита. Остановка закрывает порты и контексты. Текстовая история на экране ограничена 200 сообщениями; старые доступны страницами. Изображения вне области просмотра освобождаются.

Режим WebView2 `MemoryUsageTargetLevel=Low` включается у скрытого/минимизированного окна без звонка и возвращается в Normal при открытии или активном звонке. Это рекомендация среде выполнения, а не жёсткий лимит RAM. JS и сеть не приостанавливаются; входящие звонки продолжают обрабатываться. Убраны флаги принудительной фоновой активности.

При подключении микрофона возобновляется host AudioContext. Если DSP не запускается, сохраняется исходная дорожка и показывается предупреждение. Исчезнувший сохранённый USB-вход допускает повторную попытку системного входа только при `NotFoundError`/`OverconstrainedError`; отказы приватности не обходятся. Профиль WebView2 не сохраняет собственное решение о микрофоне и камере поверх разрешений Coherent. В настройках доступна временная проверка сигнала без самопрослушивания.

Раз в минуту в локальный ротируемый `diagnostics/desktop.jsonl` записываются только агрегированные счётчики private/working memory процессов среды WebView2, число процессов, видимость и признак звонка. Содержание сообщений, медиа, имена устройств и ключи не записываются. Путь: `%LOCALAPPDATA%\Coherent\diagnostics\desktop.jsonl`. Сам случай 6–7 ГБ и конкретный Fifine ещё необходимо подтвердить на Windows 11: на Linux их нельзя достоверно воспроизвести.

Ветка Windows-клиента: `windows-client`. 25 октября владелец разрешил push в отдельную ветку и публикацию первого выпуска **0.1.0**. Дальнейшая нумерация — 0.1.1, 0.1.2 и далее. Надпись «Когерент в разработке» сохранена; выпуск не объявляется стабильным 1.0.

## Установленная причина вылета

Первый panic восстановлен отдельным воспроизведением `start_system_audio` без запуска WGC. Синхронная команда вызывала `tokio::spawn` на UI/COM-потоке без Tokio reactor. Далее возникал вторичный `panic in a function that cannot unwind` и завершение с `0xc0000409`. Старый panic hook перезаписывал первичное сообщение вторичной паникой, поэтому стек ошибочно указывал в первую очередь на COM/WebView2.

Исправление: задача запускается через Tauri async runtime; блокирующие операции и join вынесены с UI-потока. Native capture получает RAII-владение до запуска помпы. Stop ждёт завершения callback до освобождения контекста. Проверены десять последовательных локальных циклов; добавлена регрессия на обычном потоке без Tokio context.

Исходное воспроизведение и журналы хранятся в игнорируемой `.codex/diagnostics/`. Они не входят в Git или установщик.

## Изменённый медиапуть

Основное видео использует WGC → BGRA → read-only SharedBuffer → копию VideoFrame → canvas track → WebRTC. JPEG/Base64 устранены из основного потока. Есть две копии пикселей и работа canvas; аппаратное ускорение определяется WebView2/WebRTC. Прямая GPU-текстура и гарантированное аппаратное кодирование не заявляются.

Общая память ограничена приблизительно 32 MiB на поток. COM остаётся на UI-потоке, producer владеет независимым mapped view. ACK отправляется после чтения кадра. Устаревшие capture ID не могут остановить новую сессию. Отмена закрывает треки, публикации, worklet, AudioContext, mapping и обработчики. При сбое renderer нативный захват останавливается отдельно от COM callback.

Статичное окно теперь перерисовывает сохранённый canvas после публикации и раз в секунду: новый получатель больше не ждёт изменения исходного окна для первого изображения.

В первоначальном замере движущийся источник дал примерно 14–17 FPS при цели 30. После исправления порога пропуска кадров около границы таймера установленный клиент передал весь экран с измеренными 25 FPS. Значения «30/60» остаются целевым пределом и не выдаются за гарантированную частоту. Для аудио с E2EE `totalAudioEnergy` оказался нулевым даже при ненулевом декодированном звуке, поэтому проверка выполнена анализатором принимаемой дорожки, а не по этому полю статистики.

Проверка проведена двумя отдельными служебными аккаунтами, без звонков и сообщений от имени владельца. Исходный зашифрованный сеанс установленного клиента восстановлен с проверкой совпадения файла; после запуска подтверждены авторизованный интерфейс и отсутствие тестового аккаунта. Служебный веб-клиент вышел из аккаунта и закрыт. Временные исполняемые файлы, тестовый звук и старый preview удалены. Остаётся одна зарегистрированная установка и один текущий установщик `Coherent-setup.exe` с подписью. Учётные данные служебных аккаунтов в игнорируемой папке `.codex/qa` защищены Windows DPAPI.

Подробные замеры находятся в `.codex/qa/e2e-installed-monitor.json`, `e2e-shared-long.json`, `e2e-shared-audio-tone.json` и `e2e-coherent-audio-exclusion.json`. Журналы, служебные сеансы и материалы проверки не входят в установщик или Git.

## Проверки, необходимые до стабильного выпуска

Нужны другой физический ПК/телефон, длительный тест сети/сна, 4K/60 и остальные кодеки на соответствующем оборудовании. Два клиента текущего E2E работали на одном физическом ПК, соединяясь через сервер. Нативное меню значка в трее и визуальное появление баннера Windows ещё требуют отдельного ручного подтверждения. Переход через встроенное обновление с опубликованной 0.1.0 на 0.1.1 подтверждён владельцем и последующей проверкой установленного клиента. Локальная проверка подписи, отказ при изменении пакета и автоматические проверки откладывания обновления во время звонка также пройдены. На проверенном ПК экспериментальный локальный пакет 0.2.0 ранее заменён публичным 0.1.0 с сохранением идентификатора приложения.

## Обновления и настройки 0.1.1

- Исходники перенесены в ветку `windows-client`; README описывает Windows-клиент, а инструкции веб-разработчика вынесены отдельно. `main` при публикации не менялся.
- В начале настроек приложения показаны текущая и доступная версии, время проверки, прогресс скачивания и отдельная установка с перезапуском. Скачивание разрешено во время звонка; установка откладывается до его завершения. Подпись проверяется до появления действия установки.
- Тестовые уведомления и проверки медиа скрыты в свёрнутой диагностике. Компонент загружается при раскрытии; проверки сами не запускаются.
- Пройдены 24 frontend-теста, два Rust-теста, Clippy с запретом предупреждений и локальная сборка подписанного NSIS-пакета. Проверены ошибки подписи и установки, повторное скачивание, сохранение проверенного пакета при повторной проверке, начало звонка во время загрузки и скрытие диагностики.
- Публичные установщик, подпись, `latest.json` и контрольные суммы скачаны с GitHub и сверены с локальной сборкой. Подпись с версией 0.1.1 принята библиотекой проверки Tauri; изменение байта установщика отвергнуто.
- Установленный клиент 0.1.0 обнаружил опубликованную 0.1.1 через штатную проверку и показал кнопку установки. Владелец выполнил обновление внутри приложения и подтвердил его работу. После этого проверены версия 0.1.1 в Windows, запуск сборки `f676511b82e2`, авторизованный интерфейс и блок «Установлена последняя версия Coherent». Контрольные суммы зашифрованного сеанса и четырёх файлов настроек до и после совпали.
- В старом 0.1.0 баннер обновления с `top: 12px` частично перекрывался заголовком окна высотой 36 px. В 0.1.1 это уже устранено: баннер имеет `top: 48px`, расположен справа, а прежнее правило удалено из общего CSS. Блок обновлений в настройках установленной 0.1.1 визуально проверен: заголовок, версия и кнопка проверки видны целиком.

## Доработки после повторной проверки владельцем, 25 октября

- Удалены устаревшие ограничения только Windows в настройках: 720p, 15 FPS, VP8 и 6 Мбит/с. Доступны те же настройки, что в веб-клиенте: до 4K, 15/30/60 FPS, 1–50 Мбит/с, кодеки по возможностям WebRTC. Основной SharedBuffer-путь получает выбранные параметры; ограниченный fallback для старого runtime остаётся совместимым путём, не основным режимом. Подтверждённые ранее 25 FPS не являются гарантией 60 FPS.
- В установленном интерфейсе подтверждены исходное разрешение, 30 FPS, сохранённые 20 Мбит/с и доступный выбор всех четырёх кодеков: VP8, H.264, VP9, AV1. Настройки владельца при проверке не менялись.
- Собственное перечисление окон учитывает DWM cloaking, стили/владельцев, служебные процессы и обычные свёрнутые приложения. Для UWP определяется процесс приложения внутри frame host. Минимизированное окно показывается с отметкой и восстанавливается только при запуске показа; превью его самопроизвольно не разворачивает. Список обновляется каждые две секунды и при возврате фокуса. Локальная проверка увидела обычные приложения, включая свёрнутый Telegram; TextInputHost/SystemSettings/ApplicationFrameHost в списке отсутствовали.
- Прежний тест локального WebAudio-тона не доказывал исключение принятого голоса. Теперь исключается фактический браузерный процесс главного WebView2 и его дерево, полученное через официальный `BrowserProcessId`. Добавлена отдельная локальная диагностика с принятой WebRTC-дорожкой и воспроизведением через HTMLAudioElement. Её нельзя приравнивать к повторному звонку на другом физическом устройстве.
- Проверка окончательно установленной сборки: принятый WebRTC-сигнал 1800 Гц воспроизведён локально; в системном захвате уровень на этой частоте составил −72 дБ. Одновременно отдельный процесс воспроизводил контрольные 1000 Гц: они присутствовали в захвате на −26 дБ. Получено 212 пакетов, итоговый пик native PCM — 1737, захват остановлен без ошибки. Это подтверждает изоляцию принятой HTML/WebRTC-дорожки с сохранением внешнего звука на данном ПК; повторный внешний звонок владельца остаётся отдельной проверкой. Текст результата сохранён в игнорируемой `.codex/qa-fixes/call-audio-isolation.txt`, кадры и PCM не сохранялись.
- Выключены навигационные жесты WebView2 и overscroll на поверхности приложения; внутренние области сохраняют обычную прокрутку. Физический тачпад отдельно не проверен.
- Заголовок окна доступен при загрузке и ошибке сети; при недоступном сервере остаются локальные настройки. Ожидание восстановления сеанса ограничено и не может бесконечно закрывать интерфейс загрузкой.
- 17 frontend-тестов и два Rust-теста прошли; проверены выбранные 4K/60/50 Мбит/с и AV1 на границе публикации, список доступных кодеков и детектор утечки тестового звука. Это автоматическая проверка передачи параметров, а не измеренный поток 4K/60/AV1.

### Перерыв в работе сервера

На VPS в 12:27 МСК Caddy получил SIGTERM и завершился с кодом 0; затем Docker и VPS перезапустились. После загрузки веб-контейнер остался остановленным, остальные пять контейнеров работали. OOM не зафиксирован; API с базой данных были здоровы. Запущен существующий `coherent-web-1`; внешние проверки сайта, `/api/v1/auth/csrf`, `/api/v1/health/ready` и LiveKit на 8443 вернули HTTP 200. Добавлена и включена служба запуска веб-контейнера после загрузки Docker; проверена без повторной перезагрузки VPS. Код сайта, база и секреты при восстановлении не изменялись. Причина, по которой Docker пропустил один контейнер, журналами полностью не установлена.
